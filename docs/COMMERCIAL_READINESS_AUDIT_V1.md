# Loadder Website Builder — Commercial Readiness Audit V1

Date: 2026-09-24
Scope: `src/components/store-studio-v16/` (incl. `templates/`), `src/pages/StoreWebsiteStudioPageV16Core.tsx`, `server/app/routes/site-projects.mjs`, `server/app/routes/public-sites.mjs`, `server/app/routes/auth.mjs`, `server/app/commerce/` (incl. `v2/`), and the site services these files call directly (`site-project-service.mjs`, `site-project-repository.mjs`, `site-domain-service.mjs`, `site-lead-service.mjs`, `ecommerce-service.mjs`, `store-public-presentation.mjs`, `store-site-html.mjs`, `corporate-site-html.mjs`, `v16-patch-engine.mjs`/`v16-patch-policy.mjs`).

Account/workspace creation, billing, and the CRM/Marketing/Business Brain modules are **outside this audit's file scope** and are not assessed below — where the customer journey depends on them, that is stated explicitly rather than assumed.

## 1. Customer journey test

| Step | Result | Evidence |
|---|---|---|
| Create account/workspace | **NOT ASSESSED** | Outside the audited file set (no auth/signup/workspace-provisioning page was in scope). `auth.mjs`'s own `/api/auth/status` endpoint self-reports `productionReady:false, otpDelivery:"not-connected"` — OTP codes are generated but not actually delivered by SMS/email in this build, which is directly relevant to real signup even though the signup UI itself wasn't inspected. |
| Create website | **MISSING** | `POST /api/site-projects` exists and works (`site-projects.mjs:26`, backed by `site-project-service.mjs`'s tested `create()`), but `StoreWebsiteStudioPageV16Core.tsx` never calls it — its load effect only does `GET /api/site-projects`, picks the first project matching the current `siteKind`, and **throws** ("پروژه فروشگاهی پیدا نشد") if none exists. There is no "new site" button or flow anywhere in the audited Studio code. A customer cannot create their first STORE site from the Website Builder itself today. |
| Select template | **MISSING** | `templates/registry.ts`'s `TEMPLATES` catalog and `createConfigFromTemplate()` are real, tested, and produce a correct independent `StudioConfig` (verified in this session's acceptance tests). But zero files in the audited scope call `createConfigFromTemplate()` or reference `"template"` at all — `grep -rl "template" src/components/store-studio-v16/ src/pages/StoreWebsiteStudioPageV16Core.tsx` returns nothing outside the `templates/` directory itself. The capability exists; no customer can reach it. |
| Edit design | **PASS** | `InspectorPanel.tsx`'s `DesignEditor`, `HeaderEditor`, `HeroEditor`, and per-section editors all patch a live `StudioConfig` through `StudioActions`, and `StudioCanvas.tsx` renders the same config for editor, preview and public runtime by construction — verified working throughout this session. |
| Add products | **PASS** | `StoreWebsiteStudioPageV16Core.tsx` has a real "create product" dialog that calls `POST /api/stores/:id/products` and refreshes the catalog; `productsForSection()` in `config.ts` and the mirrored logic in `store-site-html.mjs` correctly bind sections to that real catalog by source (featured/latest/discounted/manual) — confirmed end-to-end in this session's acceptance tests with real catalog rows. |
| Publish | **PASS** | `POST /api/site-projects/:id/publish` (`site-projects.mjs:173`) → `site-project-repository.mjs`'s transactional `publish()`, which appends an immutable `site_publish_versions` row. Confirmed working end-to-end (real DB, real publish, real render) in this session. |
| Connect domain | **PARTIAL, backend-only, unverified** | Backend exists: `POST/GET/DELETE /api/site-projects/:id/domains` → `site-domain-service.mjs`. But `grep -rl "domain" src/components/store-studio-v16/ src/pages/StoreWebsiteStudioPageV16Core.tsx` returns **nothing** — there is no UI anywhere in the audited Studio to enter or manage a custom domain. Even if there were: `site-domain-service.mjs.attach()` just normalizes the string and marks it `ACTIVE` in the DB — there is **no DNS ownership verification (no TXT/CNAME challenge)** and **no TLS/SSL certificate provisioning** anywhere in this service. A customer could "connect" a domain they don't own, and even a legitimately owned domain would need certificate handling done entirely outside what this audit found. |
| Receive orders | **PARTIAL** | Order *creation* is solid: `POST /storefront/carts/:cartId/checkout` (`auth.mjs:56`) creates a real `ecommerce_orders` row with server-derived money, capability-hash receipt access, and rate limiting — confirmed working end-to-end this session. But two real gaps: (1) **no online payment gateway is wired in** — `paymentProvider` is hardcoded to `"manual"` in the checkout route, and the well-built `payment-attempt-service.mjs` + `defineCommercePaymentProviderAdapter` contract (idempotent, money-safe, provider-agnostic) is imported **only by tests** (`grep -rl "createPaymentAttemptService" server` → test files only) — no route ever calls it. (2) **no order/lead notification exists** — `grep -rli "sendmail\|nodemailer\|sendEmail\|webhook\|smsService" ecommerce-service.mjs site-lead-service.mjs server/app/commerce` returns nothing; a merchant has no email/SMS/webhook telling them an order arrived, they'd have to poll a dashboard. |

**Bottom line:** a real customer cannot get from signup to a live, payable store using the Website Builder alone today. The two hard stops are *creating a site* and *selecting a template* — both have complete, tested backend/logic layers with **no UI path to reach them**.

## 2. Production blockers

### P0 — cannot sell without fixing
1. **No "create new site" flow in the Studio.** `StoreWebsiteStudioPageV16Core.tsx` assumes a project already exists. Without this, a new customer has literally nothing to edit.
2. **No template-selection UI.** `createConfigFromTemplate()`/`TEMPLATES` are built and tested but unreachable — "Loadder Commerce Modern V1" cannot be chosen by anyone through the product today.
3. **No real online payment gateway.** Checkout is hard-locked to `"manual"`. The money-safe adapter contract (`payment-attempt-service.mjs`) exists but is wired to nothing. Most commercial customers expect to accept a real card/wallet payment at checkout, not coordinate payment manually per order.
4. **No order/lead notification.** A merchant who isn't actively watching the dashboard will not know a sale happened. This alone will lose orders in practice (unfulfilled, unnoticed).
5. **Domain connection has no ownership verification or TLS provisioning.** `site-domain-service.mjs.attach()` is a bare string insert. Selling "connect your own domain" as a feature on top of this is a support and security liability (domain hijack risk between tenants is only prevented by a uniqueness constraint, not by proving the requester owns the domain).
6. **OTP delivery is not connected** (`/api/auth/status` → `otpDelivery:"not-connected"`, `productionReady:false`, self-reported by the code). If this reflects the real signup path, no real customer can complete authentication today.

### P1 — important before scaling
1. **`server/app/commerce/v2/*` (cart, checkout, pricing, promotion, inventory-reservation, fulfillment, returns/refunds, customer-account, order, catalog engines — 10 files) is entirely test-only.** `grep` confirms every one of these is imported exclusively by `server/test/commerce-v2-*.test.mjs` files; the live storefront (`auth.mjs` + `ecommerce-service.mjs`) uses a separate, simpler, hand-rolled cart/checkout/coupon implementation instead. Promotions, inventory reservation, real fulfillment tracking, returns/refunds, and customer accounts — all present and well-tested in `commerce/v2` — are **not available to a real merchant today** because nothing routes to them. (The one exception: `financial-ledger.mjs` is genuinely wired into `ecommerce.mjs`/`canonical-commerce.mjs`/`site-builder-control-plane.mjs`.) This needs a product decision: wire `v2` in, or delete/archive it — maintaining two parallel commerce stacks is itself a growing liability.
2. **No SEO essentials beyond `<title>`/`<meta description>`.** No Open Graph tags, no canonical link, no JSON-LD product structured data, no generated `sitemap.xml` or `robots.txt` anywhere in the audited render paths (`store-site-html.mjs`, `corporate-site-html.mjs`, `public-sites.mjs`). Competing builders generate all of these automatically.
3. **`category-grid`/`brand`/flash-sale fields are not in the Ask Loadder patch allow-list** (`v16-patch-policy.mjs`) — natural-language editing silently can't touch the newest section types yet (known, previously documented in `.claude/current-state.md`).
4. **Ask Loadder is a keyword/regex matcher, not an LLM** despite the branding (previously documented finding, `v16-instruction-translator.mjs`) — fine functionally, but a mismatch with customer expectations if marketed as AI-assisted editing.
5. **Design Copilot reads the wrong content path** (`content.visualStudio` instead of `content.storeBuilderV16`) — previously documented, still unfixed; the one genuinely AI-backed assist feature doesn't work against real V16 projects.
6. **No rate limiting on public `GET /sites/:id`/custom-domain rendering** (`public-sites.mjs`) — it has caching (`ETag`, `max-age=60`) which helps, but no app-level throttle the way the storefront mutation routes in `auth.mjs` have.

### P2 — future improvements
1. STORE `Footer` (client canvas) and SSR footer both ignore `config.footer.text`, showing fixed copy instead — cosmetic, previously documented.
2. `"trust"`-typed sections render through the generic title/subtitle fallback box in `StorefrontCanvas`, not the icon-badge `TrustStrip` design — cosmetic mismatch, previously documented.
3. No structured/centralized logging or error tracking (Sentry/Datadog/OpenTelemetry/etc.) found anywhere in the audited backend files — errors go to `console.error` only, with no request correlation ID.
4. Adding a new section type still requires hand-editing ~4-5 files by hand (`types.ts`, `site-types.ts`, two maps in `StoreWebsiteStudioPageV16Core.tsx`, `StudioCanvas.tsx`, `InspectorPanel.tsx`) — workable at current scale, but a real scaling cost as the section library grows (previously documented in the Template System audit).

## 3. UX gaps vs. Shopify / Webflow / Wix

**Onboarding.** All three competitors put a template-selection screen as literally the first thing after signup, with a live preview before any commitment. Loadder has the *data model* for this (`WebsiteTemplate`, `createConfigFromTemplate()`) but no screen at all — today a project must already exist before the Studio loads. This is the single widest gap in the onboarding category.

**Editing.** The core direct-manipulation model (click an element on the canvas, edit in a side panel, live preview) is architecturally comparable to Wix/Webflow's canvas editors — `StudioCanvas.tsx` genuinely renders one truth for editor/preview/public runtime, which is a real strength (Shopify's theme editor, by contrast, has a well-known preview/live drift problem this design avoids by construction). Where Loadder falls short: no drag-to-reposition sections relative to each other beyond up/down move buttons, no undo/redo keyboard shortcuts visible in the audited files (revision history exists and is restorable via API, but there's no obvious one-click "undo" in the toolbar), and the section library (a fixed hardcoded union) is much smaller and slower to extend than Webflow's component system or Shopify's app-extensible sections.

**Publishing.** Publish-with-immutable-versioning-and-rollback (`site_publish_versions`, `publish-rollback` endpoint) is genuinely on par with or better than typical competitor publish models in terms of data safety. The gap is entirely in domain connection UX: Shopify/Wix/Webflow all walk the merchant through DNS records with live verification status ("Checking...", "Verified ✓", TLS auto-provisioned in the background). Loadder has none of that surfaced to the user, and the backend doesn't verify ownership at all yet.

**Commerce.** Shopify's checkout is the category benchmark: real gateways, abandoned-cart recovery, tax/shipping rules, order notifications, customer accounts. Loadder's checkout is correctness-first (server-derived money, idempotency, capability-based access — genuinely solid engineering) but commercially thin: manual payment only, no notifications, and a whole second commerce engine (`v2`) sitting unused that already has promotions/inventory-reservation/fulfillment/returns/customer-accounts built and tested. The fastest path to closing this gap is very likely wiring up what already exists in `v2` rather than building new commerce features from scratch.

## 4. Technical readiness

**Security.** Genuinely strong in the parts that were touched this session: server-derived money on every commerce mutation (`payment-attempt-service.mjs` explicitly rejects client-supplied `amountMinor`/`currency`), capability-hash-gated public cart/order access (no session needed, but also no way to guess another customer's cart), rate limiting on OTP/lead/checkout routes, correct CSP/`X-Content-Type-Options`/`Referrer-Policy`/`X-Robots-Tag` headers on public and preview rendering, and a real Commerce-truth patch allow-list (`v16-patch-policy.mjs`) that blocks price/inventory/payment fields from any natural-language or structured-patch path. Weak points: domain "ownership" is unverified (see P0 above); no rate limit on public site GET routes; no CSRF consideration documented anywhere in the audited auth flow (session cookie is `httpOnly`/`sameSite:lax`, which mitigates most CSRF risk by default, but this wasn't an explicit design decision found in the code, just a byproduct of the cookie flags).

**Performance.** Public rendering is real server-rendered static HTML (not client-side React hydration) with `ETag`/`Cache-Control: max-age=60, stale-while-revalidate=300` — good, CDN-friendly defaults. No lazy-loading gap found (`loading="lazy"` used consistently in `store-site-html.mjs` item/product grids). No evidence of a CDN/edge layer or image optimization/resizing pipeline in the audited scope — images are served at whatever URL was uploaded, uncompressed/unresized by the platform.

**SEO.** Basic (`<title>`, `<meta description>`) only — no Open Graph, no JSON-LD, no sitemap/robots generation (see P1 above). This is a meaningful gap for an ecommerce product, where Product structured data materially affects Google Shopping/rich-snippet visibility.

**Reliability.** The persistence/patch/publish/revision stack is the most mature part of the codebase: append-only revisions with SHA-256 + idempotency keys, transactional publish, CAS-guarded draft saves (`expectedRevision` conflict detection), deterministic patch validation. This part looks production-grade. The commerce side is bifurcated (see P1) — the live path is simpler and less feature-complete than the well-tested-but-unused `v2` engines.

**Monitoring.** No APM, structured logging, or error-tracking integration found anywhere in the audited files — `console.error` is the only signal, with no request correlation ID, no alerting. If something breaks in production (e.g., a checkout failure), there is currently no mechanism in the audited scope for anyone to find out except a customer complaint or manually grepping logs.

## 5. Next 30-day roadmap (prioritized)

1. **Week 1 — Unblock the core journey.** Build the "create new site" flow (call the already-working `POST /site-projects`) and the "select a template" screen (call the already-working `createConfigFromTemplate()`), wired into `StoreWebsiteStudioPageV16Core.tsx`'s current single-project-per-workspace load path. This is almost entirely UI work against existing, tested backend logic — the highest-leverage fix available.
2. **Week 1-2 — Order visibility.** Add at minimum an email notification on new order/lead (even a simple transactional-email call from `ecommerce-service.mjs`'s `checkout()` and `site-lead-service.mjs`'s `submit()`). Small, high-impact, directly prevents lost sales.
3. **Week 2 — Payment gateway decision + first integration.** Pick one real gateway relevant to the target market, implement it against the already-built `defineCommercePaymentProviderAdapter` contract, and wire `payment-attempt-service.mjs` into the checkout route as an alternative to `"manual"`. The hard money-safety work is already done; this is "write one adapter and one route branch."
4. **Week 2-3 — Domain connection, done properly.** Add DNS ownership verification (a TXT/CNAME challenge value returned by `attach()`, checked before flipping status to `ACTIVE`) and at least a manual/scripted path to TLS provisioning; surface a "Connect domain" screen in the Studio with live verification status.
5. **Week 3 — Commerce-v2 decision.** Spend a day deciding whether to (a) wire `commerce/v2`'s promotion/inventory-reservation/fulfillment/returns/customer-account engines into the live routes, or (b) archive them. Carrying two parallel, un-reconciled commerce stacks is itself a growing maintenance cost; this should be resolved before adding more commerce surface area.
6. **Week 3-4 — SEO essentials.** Add Open Graph tags, canonical link, per-product JSON-LD, and a generated `sitemap.xml`/`robots.txt` to `store-site-html.mjs`/`corporate-site-html.mjs`/`public-sites.mjs`. Mechanical, well-scoped, meaningful for real-customer discoverability.
7. **Week 4 — Minimum monitoring.** Add one error-tracking integration (even a lightweight one) and a request-correlation ID in logs, so a production incident is discoverable before a customer reports it.
8. **Ongoing, lower priority this month:** Ask Loadder patch-allow-list update for the new section types; Design Copilot content-path fix; domain-service and public-GET rate limiting.
