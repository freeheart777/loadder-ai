# Website Builder V16 — Template System Audit

Scope: `src/components/store-studio-v16/*`, `src/pages/StoreWebsiteStudioPageV16Core.tsx`, and the V16 persistence/schema files (`server/app/services/site-project-service.mjs`, `site-page-model.mjs`, `site-document-patch-service.mjs`, `v16-patch-engine.mjs`, `v16-patch-policy.mjs`, `site-document-revision-service.mjs`, `store-public-presentation.mjs`, and the `042/043/090/091/049` migrations). No repository-wide scan performed; a targeted grep for "template"/"theme" inside this same scope confirmed no dedicated template/theme table or file exists anywhere in it.

## 1. Current template architecture

**How sections are defined.** `SectionConfig["type"]` (`types.ts`) is a closed TypeScript union — `products | banner | trust | text | spacer | about | services | portfolio | team | text-image | cta | contact` — not a data-driven registry. Adding a section type means hand-editing four separate files that must stay in sync by convention, not by a shared source of truth: the union itself, `StudioCanvas.tsx`'s render switch, `InspectorPanel.tsx`'s editor-form switch, and `config.ts`'s `newSection()` factory. `site-types.ts` gates which of these types each *site kind* may use (`SITE_TYPES.STORE.sectionTypes` vs `SITE_TYPES.BUSINESS.sectionTypes`) — this per-kind allow-list is the closest thing to a template contract that exists today.

**How themes are stored.** There is no theme entity. `DesignConfig` (~16 flat tokens: colors, fonts, radii, spacing, scale) lives inline inside `StudioConfig.design`, itself inline inside one project's own `site_projects.content_json` document. A "theme" is indistinguishable from "this one project's current design values" — it cannot be named, saved independently, cataloged, or applied to a second project. The only "starting theme" that exists is a single hardcoded default object per site kind (`designDefaults`/`sectionDefaults` for STORE, `corporateHeroDefaults`/`corporateSectionDefaults` for BUSINESS, all in `config.ts`), applied exactly once, only when a brand-new project has no `storeBuilderV16` content yet (`restoreConfig()`'s fallback branch).

**How components are registered.** Not registered — `StudioCanvas.tsx` is one file containing every section renderer as a private function, selected by inline `if`/ternary chains (`StorefrontCanvas`, `CorporateCanvas`). `InspectorPanel.tsx` maintains its own parallel `if`-chain choosing which editor form matches a given `section.type`. Nothing maps a `type` string to `{renderer, editorFields, defaults}` in one place; the two files are kept consistent by hand.

**How pages are generated.** A page is generated by copying one of exactly two hardcoded arrays (`defaultSectionsFor()` in `config.ts`: `sectionDefaults` for STORE, `corporateSectionDefaults` for BUSINESS) — there is no composition step beyond "start with this one fixed array." Server-side, `site-page-model.mjs`'s `readPages()`/`validatePages()` only handles slug/nav/SEO bookkeeping for pages that already exist in the document; it has no concept of, or opinion about, section content, and cannot generate a new page from anything resembling a template.

## 2. Can the system support reusable templates?

**NO** — not today, but nothing in the underlying document model blocks adding it.

There is no way to (a) name/save/catalog a starting configuration independent of any one project, (b) reference that catalog entry when creating a new project — `site-project-service.mjs`'s `create()` only ever seeds from `ensureWebsitePlatformContent()`'s one fixed per-archetype default, never from an arbitrary saved document — or (c) resolve a section type through a registry rather than duplicated hardcoded switches. None of the three exist in the audited scope.

What already exists and *is* genuinely reusable groundwork: `StudioConfig`/`content.storeBuilderV16` is already a plain, versioned, JSON-serializable object with zero embedded code — a template is structurally "one more `StudioConfig`-shaped JSON blob," the right shape to build on without a rewrite. The structured-patch validation layer (`v16-patch-policy.mjs`'s `ALLOWED` table, section-type-aware already) and the append-only revision/publish pipeline are more rigorous than a template feature strictly needs, and both are reusable as-is once a template concept exists.

## 3. Gap: current V16 builder vs. a Shopify/Webflow-style template system

| | Shopify / Webflow | Loadder V16 today |
|---|---|---|
| Starting design | Packaged, versioned, catalog of installable/switchable themes | One hardcoded default per site kind, no catalog, no switching |
| Section definition | Schema files (JSON) that generate the merchant editor UI automatically | Hand-written TS union + duplicated hardcoded switches (`StudioCanvas.tsx` + `InspectorPanel.tsx`) |
| Component reuse | Independent, nameable, droppable component library | No registry; components are private functions inside one file |
| Creating a new project from a template | First-class flow | Does not exist — `create()` always seeds the one fixed archetype default |
| Template vs. instance separation | Theme code and store content are decoupled; a theme can be updated without touching store edits | No separation — a "template's" sections and a store's edited content are the same JSON object |
| Persistence rigor | Varies by platform | Already ahead: append-only revisions, idempotent structured patches, Commerce-truth protection at the patch-policy layer — reusable as-is for a template feature |

The concrete missing pieces, in priority order: (1) a template/theme catalog and its storage (no `site_templates` table or equivalent exists in the audited migrations — confirmed via grep), (2) a section *registry* replacing the duplicated hardcoded switches, (3) a "create project from template" seed path, (4) a catalog/preview UI for choosing among multiple starting designs, (5) template-vs-instance decoupling so updating a template doesn't require touching already-built stores.

## 4. Plan: "Loadder Commerce Modern V1"

Mapping the Stitch reference sections against what already exists in the STORE section registry (`site-types.ts`):

| Stitch section | Status | Note |
|---|---|---|
| Hero banner | **Exists** | `HeroConfig`, site-wide singleton — reusable as-is. |
| Trust badges | **Exists** | `trust` section type — reusable as-is. |
| Flash sale | **Partial** | A `products` section with `productSettings.source: "discounted"` already models this (`Core.tsx`'s existing "تخفیف‌های ویژه" quick action, `addDiscountSection()`). Missing: a countdown-timer field — a new data field, not a new mechanism. |
| Category grid | **Missing** | No `category` concept exists as a section at all; `ecommerce_products.category` is only ever used as a flat text filter, never surfaced as a browsable grid. New section type needed. |
| Product grid | **Exists** | `products` section type, already fully data-driven from the real catalog. |
| Product card | **Exists as a component, not standalone** | `ProductCard` in `StudioCanvas.tsx` only renders inside a `products` section; there is no independent "single product" or "product spotlight" section type. |
| Brand section | **Missing** | No `brand` section type; `Product.brand` is only a text label/filter, never rendered as its own section. |
| Footer | **Exists** | `FooterConfig`, site-wide singleton — reusable as-is, though presentation-only today (no link columns/social icons). |

**Plan (design only, no code changed):**

1. Add exactly two new section types to the closed union and to STORE's `sectionTypes` allow-list: `category-grid` and `brand`. Each is plain data fields only, following the existing pattern of every current type — no new architectural mechanism required.
2. Add the "flash sale" countdown as new sibling fields (e.g. `saleEndsAt`, `saleLabel`) on `SectionConfig`, following the exact precedent already set by `visibleProductCount`/`productImageSize`: those two fields were deliberately kept as patch-reachable siblings *outside* the protected `productSettings` container specifically so Commerce-truth protection in `v16-patch-policy.mjs` never has to change shape to add a presentation lever. The same convention applies cleanly here.
3. Define "Loadder Commerce Modern V1" as nothing more than one additional static JSON object shaped exactly like today's `sectionDefaults`/`corporateSectionDefaults` — an ordered `SectionConfig[]` in the Stitch order (hero → trust → flash-sale products → category grid → product grid → brand → footer) plus one `DesignConfig` for its visual identity. As a plain data literal with no logic and no model call anywhere in its definition, this is deterministic and AI-independent by construction, and schema-driven because it is exactly the same schema every other section already uses — it satisfies all three required constraints without inventing anything new.
4. **Explicitly deferred, not part of this plan:** *where* that JSON object should live so it becomes reusable across projects rather than copy-pasted per new store (the actual template-catalog storage/retrieval mechanism identified as the gap in §2–§3). Auditing that gap was this document's job; resolving it — e.g. a `site_templates` table, or a static in-code catalog, or something else — is the next decision point and needs its own go-ahead before implementation.
